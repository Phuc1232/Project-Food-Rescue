1. KẾT QUẢ
- GET /api/v1/admin/accounts?q&role&status&page&size — tìm theo một phần email, vai trò, trạng thái; mới nhất trước; không có thông tin đăng nhập.
- GET /api/v1/admin/accounts/{id} — vai trò, cửa hàng sở hữu (OWNER) và phân công nhân viên (STAFF, trạng thái, quyền), trạng thái + lý do,
  số đơn tồn đọng (khách / cửa hàng sở hữu), 50 mục lịch sử AUTH + ACCOUNT. Không có hash/token.
- POST /api/v1/admin/accounts/{id}/status {LOCK|UNLOCK, reason, outstandingPlan?}: ACTIVE ⇄ LOCKED; khóa thu hồi mọi phiên và có hiệu lực
  request kế tiếp (converter JWT đòi ACTIVE); còn đơn PENDING_PAYMENT/CONFIRMED/HANDOVER_IN_PROGRESS/PENDING_NO_SHOW mà không có
  outstandingPlan → 409 OUTSTANDING_WORK (fieldErrors customerOrders/storeOrders = số lượng). Mở khóa không đổi cửa hàng, vai trò,
  phân công. Tự khóa → 403. Trạng thái nguồn sai → 409. Khóa dòng account → hai admin đồng thời: một 200, một 409.
- V8: account.status_reason, account.status_changed_at. Audit ACCOUNT_LOCKED / ACCOUNT_UNLOCKED (entity ACCOUNT, actor admin,
  before/after, reason, outstandingPlan); thu hồi phiên ghi thêm AUTH SESSIONS_REVOKED_BY_ADMIN.

4. KỊCH BẢN BẤM THỬ TRÊN SWAGGER
 1. Token ADMIN: Admin accounts › GET /api/v1/admin/accounts?q=<một phần email> → thấy tài khoản U.
 2. GET /api/v1/admin/accounts/{id U} → roles, stores, outstanding*, history (REGISTERED, EMAIL_VERIFIED, LOGIN...).
 3. POST .../{id U}/status ví dụ "lock" → 200 LOCKED, statusReason. Dùng token cũ của U gọi Account › GET /me → 401; đăng nhập U → 401.
 4. Gửi lại "lock" → 409. Gửi với id của chính admin → 403.
 5. Ví dụ "unlock" → 200 ACTIVE; U đăng nhập lại được; cửa hàng của U (nếu SUSPENDED) vẫn SUSPENDED.
 6. (Có đơn tồn đọng — hiện chỉ tạo được bằng SQL tới T5.2) "lock" → 409 OUTSTANDING_WORK; "lockWithPlan" → 200.
